# 红蓝具体实现 A

实现 A 使用仓库内轮次记录、短期角色分支、Git worktree 和独立 Agent 上下文运行红蓝。

它可以被不同项目使用，不属于某一个项目。项目中的一次开发只是实现 A 的一次运行。

## A 固定的内容

- 长期功能语义保存在项目的 `docs/contracts/`
- 一轮红蓝的协调信息保存在 `docs/dev-runs/<功能点>-v<版本>.md`
- 红方、蓝方和规划方合流分别使用短期分支与 worktree
- 红蓝从同一个已经提交的基线开始
- 红蓝使用独立 Agent 上下文，不能读取对方在本轮产生的增量
- 规划方在独立的 integration worktree 合流双方产物
- 原轮次失去独立性时增加版本并开始新轮次

## 项目需要提供的内容

采用 A 的项目需要提供：

- 本轮功能契约和可观察边界
- 红蓝可以读取的共同材料
- 红蓝各自允许修改的路径
- 测试、运行和验收方式
- 开发 Harness 中启动独立 Agent 的能力
- 项目需要的人工批准位置

这些内容没有确定时，不能通过 A 自动补出。

## 一轮开发

1. 规划方根据红蓝模式判断当前功能是否能够开始，冻结功能契约。
2. 规划方建立本轮记录，并将契约、轮次记录和其他共同事实放入同一个基线 commit。
3. 从该基线建立 red、blue 和 integration 分支及 worktree。
4. 开发 Harness 使用独立上下文启动红蓝。双方读取相同的共同内容，只接收不同的角色、工作位置和写入范围。
5. 红蓝独立工作，只向规划方返回自己的产物和必要结果。
6. 规划方在 integration worktree 合流双方产物，运行验证并判断结果属于共同成立、某方偏离、契约不充分、集成设施问题或启动过早。
7. 规划方把结果和仍需继续的信息写入轮次记录。验收完成后，短期分支、worktree 和一次性记录按项目的保留规则处理。

如果契约、共同基线或独立性发生需要重开轮次的变化，不在原轮次继续拟合。增加版本，从新的共同基线重新建立三方分支与 worktree。

## 轮次记录

轮次记录使人和后来的规划方能够在 Agent 更换、会话结束或上下文压缩后恢复这一轮开发。

它需要连接：

- 使用的功能契约和共同基线
- 红方、蓝方与 integration 的工作位置
- 开发 Harness 中对应的 Agent 或任务
- 当前仍处于独立开发、合流、返工还是验收
- 红蓝产物、实际验证、失败归因和未验证内容
- 本轮独立性是否仍然成立

这些是轮次记录需要承担的功能，不是固定字段。A 不规定模板、标题、状态枚举或引用格式。项目在真实运行中根据消费者需要形成记录；出现稳定重复结构后，再决定是否提取模板。

Agent 思考、普通聊天、完整命令输出和可以从 Git 或产物恢复的重复内容不需要进入轮次记录。

轮次记录的共同输入在创建红蓝 worktree 前进入基线。红蓝开始后，规划方在红蓝 worktree 之外更新协调内容。红蓝不能读取规划方后续记录的对方进度、结论和增量引用。

## 分支与 worktree

每个功能版本使用：

- `red/<功能点>-v<版本>`
- `blue/<功能点>-v<版本>`
- `integration/<功能点>-v<版本>`

`<版本>` 表示该功能的红蓝独立轮次，不是产品发布版本。

三个分支从同一个基线 commit 建立。固定 red、blue 和 integration 分支及 worktree 不长期复用。

## 隔离

A 的基础隔离由以下内容组成：

- 独立 Git worktree
- 独立 Agent 上下文
- 红蓝写入路径限制
- 规划方对提交路径和信息边界的审查

worktree 提供版本和工作位置隔离，不是安全沙箱。多个 Agent 能够访问同一文件系统时，禁止读取对方路径仍然是开发协议。需要面对不可信 Agent 时，由采用 A 的项目增加容器、账户权限或其他真实访问控制。

## A 没有固定的内容

- 具体使用哪一种开发 Harness
- Agent 的模型和启动命令
- 功能点的命名方式
- 红蓝具体写入路径和验证命令
- 轮次记录的格式
- 人在契约冻结和合流验收中的批准位置
- 是否增加强访问隔离

项目可以选择这些内容，但不能破坏红蓝模式要求的共同基线、增量隔离、独立阶段、失败归因和可复查证据。
