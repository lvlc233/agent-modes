# 红蓝开发

红蓝开发是一种主要服务于功能开发的Agent执行模式，也可以叫loop。

主要涉及三个交互对象:
- 规划方: 负责冻结功能语义。
- 蓝方 BuildAgent（以下简称蓝/蓝方）: 负责构建功能模块
- 红方 TestAgent （以下简称红/红方）: 负责进行功能测试

蓝方和红方从相同基线出发，在看不到对方本轮增量的情况下分别形成行为测试和实现。规划方取得双方产物后合流，并根据运行结果判断这一轮的实现是否有效。

模式的核心不是“一个 Agent 写测试、另一个 Agent 写代码”，而是让测试与实现对同一功能语义作出独立解释。

补充，红方的测试并不只是说写测试代码。实际上表达的是测试这一行为本身，它可以是静态测试,运行时测试。也可以是模拟用户直接测试。

## 范围

红蓝 Agent 属于正在开发仓库的 Codex、Claude Code 或其他开发 Harness。

被开发系统不需要实现红方、蓝方、任务包、worktree 或合流调度。即使被开发系统本身也是多 Agent 系统，其中的 Agent、Session、Run、subagent 和工作区也不应该与开发红蓝使用的角色和状态混用。


## 成立条件

开启一轮红蓝前，需要同时满足：

- 功能语义已经能够冻结
- 存在红方不读取本轮实现也能使用的可观察边界
- 红方能够依据契约独立判断行为是否成立
- 红蓝双方能够读取同一份共同基线
- Harness 能够隔离双方的上下文和本轮增量产物
- 工作范围能够独立验收，又不等于一条包含大量未决内容的完整链路

不满足这些条件时，先进行研究、选择、架构设计或基础设施准备。不能为了启动红蓝而把未知事实补成契约。

以下工作通常不使用红蓝：

- 调查依赖、模型或工具实际具有哪些能力
- 比较多个产品或架构方案
- 建立目录、依赖和不包含功能判断的设施
- 纯格式化、重命名或机械迁移
- 没有稳定观察边界的内部设计

## 三个信息来源

### 规划方

规划方负责：

- 从项目事实中提取本轮共享功能语义
- 判断信息是否足以冻结契约
- 固定共同基线和双方信息边界
- 启动并维持独立轮次
- 合流双方产物
- 判断失败属于契约、测试、实现还是集成设施

规划方不直接编写同一功能的业务实现或行为测试，也不通过补写业务适配代码消除红蓝分歧。规划方自己的判断同样需要契约、产物和运行结果支持。

### 红方 TestAgent

红方读取契约和共同基线，从功能语义构造可执行的黑盒行为测试、反例和负向情境。

红方可以读取共同基线中已经存在的实现和测试，但不能读取蓝方为本轮新增或修改的实现。红方不能根据蓝方选择的内部接口、数据结构或实现步骤调整断言。

### 蓝方 BuildAgent

蓝方读取契约和共同基线，独立设计并实现功能。蓝方可以编写实现内部需要的单元测试，但这些测试不代替红方提供的独立行为证据。

蓝方可以读取共同基线中已经存在的测试，但不能读取红方为本轮新增或修改的测试。蓝方不能以通过红方具体断言作为独立阶段的实现目标。

## 契约

契约描述自然语言功能语义，不是 API 接口的自然语言版本。

一份能够启动红蓝的契约至少使双方知道：

- 功能要解决什么问题
- 哪些行为可以被外部观察
- 在什么情境下适用
- 输入、结果和失败分别表达什么含义
- 哪些结果不能发生
- 不同情境中的哪些含义必须保持相同
- 哪些内容仍然未知，因此不属于本轮假设

契约不能通过规定内部函数、类、字段、数据表、目录或实现步骤让双方得到同一份实现草图。

红方需要实际入口才能执行测试，因此契约可以规定使用者或外部系统面对的稳定入口及其行为。这里规定的是观察方式，不是内部组织。如果某项能力只能通过尚不存在的内部接口观察，应先建立稳定观察边界，再开启针对该能力的红蓝轮次。

契约充分不表示穷尽所有可能情况。它表示当前消费者能够区分正确行为、错误行为和仍未决定的行为。连续扩展仍没有产生会改变这种判断的新区别时，才适合冻结；Agent 自述“已经充分”不是证据。

## 开发单位与验收链路

一轮红蓝围绕一组可以跨情境复用的功能语义，不围绕目录模块，也不围绕单条端到端链路。

链路只提供独立验收情境。红方应使用多条链路检验同一组共享含义：

- 每条链路不依赖另一条链路的预置结果
- 尽量不重复同一组数据、操作序列和断言
- 不为每条链路建立独立的身份、消息、状态或调度实现
- 相同含义在所有链路中使用同一份定义和实现

链路之间共享被检验的语义不是交叉污染，而是检验实现能否脱离单一样例继续成立。模块可以承载这些稳定含义，但模块边界不由某条链路决定。

## 独立轮次

### 1. 冻结输入

规划方冻结：

- 模式版本
- 功能契约
- 基线 commit
- 双方共同材料及读取顺序
- 红蓝角色和允许修改的范围
- 禁止读取的本轮增量范围
- 各自完成条件和产物形式
- 最终验证入口

上述内容必须在红蓝开始前确定。红蓝双方接收相同的功能信息，只在角色、工作位置和允许产物上不同。

### 2. 建立隔离

双方从同一个基线建立独立 worktree、容器或等价工作位置，并使用独立上下文。

worktree 只隔离版本和工作位置。多个 Agent 仍可访问同一文件系统时，禁止读取对方路径只是一项开发协议，不是安全边界。面对不可信参与者时，需要容器、账户权限或其他真实访问控制。

### 3. 独立产出

红方只向规划方返回测试产物和必要说明。蓝方只向规划方返回实现产物和必要说明。双方不能直接或间接取得对方的增量、结论、失败输出或隐含接口。

缓存和 Agent 复用不能破坏隔离。同一功能及其重开轮次中，受到另一方信息污染的 Agent 不能换到对立角色。

### 4. 结束独立阶段

双方提交产物后，规划方才能同时读取两方结果。这个时间点结束本轮的独立阶段。

之后可以进行合流、审核和返工，但必须区分“独立产生的证据”和“看过对方以后产生的修正”。不能把后者重新标记成独立结果。

## 合流与归因

规划方在第三个工作位置合流实现和测试，并运行项目需要的完整验证。

结果至少分为：

### 双方共同成立

红方测试与契约一致，蓝方行为与契约一致，测试在合流实现上通过。这说明双方在已覆盖情境中形成兼容的独立解释，不表示功能在所有可能情境下必然正确。

### 红方偏离

测试要求了契约没有要求、已经排除或无法从共同基线合理得到的行为。

规划方向红方提供契约条目、可复现行为和偏离证据，不提供蓝方增量实现。

### 蓝方偏离

实现没有满足契约已经确定的行为，或者只在部分验收链路中成立。

规划方向蓝方提供契约条目、可复现行为和偏离证据，不提供红方测试源码或断言结构。

### 契约不充分

红蓝双方的解释都能从契约成立，但不能共同成立；或者公共观察边界不足以连接测试和实现。

此时不能选择其中一方的产物反向解释契约。规划方补充或纠正共同语义，冻结新基线并开启新轮次。

### 集成设施问题

合并、依赖、启动或测试环境本身失败，且不涉及功能语义。规划方可以修复集成设施，但不能借此改变测试判断或实现行为。

### 启动过早

合流暴露出功能仍处于研究、选择或观察边界设计阶段。停止红蓝，先解决前置问题。

## 返工与污染

某一方偏离且不需要修改契约时，可以让原 Agent 根据有限反馈返工。反馈只描述契约和外部行为差异。

出现以下任一情况时，当前独立轮次不能继续：

- 契约发生会改变可观察行为的修改
- 一方读取了另一方的本轮增量
- 返工必须依赖另一方的具体实现或断言
- 共同基线发生影响本轮语义的变化

需要继续时，冻结新的契约和基线，并使用没有受到对方信息污染的 Agent 开启新轮次。

只澄清措辞、且确认不改变任何可观察行为时，可以把同一澄清同时提供给双方继续原轮次。

## 证据边界

红蓝模式提供三类需要分别检查的置信度：

- 契约是否足以约束本轮行为
- 红方是否构造了有效且具有区分力的验收情境
- 蓝方实现是否满足契约并通过独立检验

测试通过不能单独替代其中任何一项。测试数量、覆盖率和通过率也不能证明红方没有遗漏关键语义。

合流报告需要保留：

- 使用的模式版本、契约和基线
- 红蓝双方的独立产物引用
- 实际执行的验证
- 覆盖的正向、负向和跨情境含义
- 失败归因及其证据
- 哪些结论来自独立阶段，哪些来自合流后的修正
- 未验证内容

## Harness 装配

模式不固定以下实现选择：

- 使用固定 worktree 还是每轮创建任务专属 worktree
- 使用 Harness 持久状态还是仓库内临时任务包
- 使用路径约束还是强访问隔离
- 由人还是规划方批准契约和合流结果
- 使用一个红方还是多个相互独立的红方

无论如何选择，装配必须保留共同基线、增量隔离、独立阶段边界、失败归因和可复查证据。无法保留这些性质的实现，只是多人协作或普通测试分工，不属于这里定义的红蓝独立开发。
